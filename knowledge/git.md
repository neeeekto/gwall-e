# Git-конвенции

Канон git-правил проекта: ветки, формат коммитов, нормы PR, «когда коммитить» — на
уровне правил, не хрупких листингов. Краткий блок GSD-практик в конце помечен как
GSD-тулинг (не общий стандарт).

## Ветки и remote

- **MUST** считать `main` основной веткой (origin/HEAD → `main`); `dev` — рабочая
  интеграционная ветка, куда вливается текущая работа.
- **SHOULD** вести фичу/задачу в отдельной ветке и вливать её в `dev` через PR; пушить
  напрямую сырые незавершённые коммиты в `main` — **WON'T**, потому что `main` — стабильная
  основная ветка; вместо этого работать в `dev`/фиче и доводить через PR.
- **MUST** держать remote `origin` указывающим на `github.com/neeeekto/gwall-e`. Заводить
  альтернативные remote'ы как канон проекта — **WON'T**; вместо этого `origin` — единственный
  источник истины для push/pull.

## Conventional Commits

- **MUST** писать сообщения коммитов в формате Conventional Commits: `type(scope): subject`.
  Базовые типы — `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `style`, `perf`.
- Образец из реальной истории репо (как ориентир формата):
  `docs(02-01): add knowledge/build.md — real build/test commands`.
- **MUST** держать `subject` в повелительном наклонении и по сути изменения; «свободные»
  сообщения без типа (`update`, `fix stuff`, `wip`) — **WON'T**, потому что они ломают
  читаемость истории и автоматический разбор; вместо этого — `type(scope): subject`.
- **SHOULD** ставить осмысленный `scope` (область изменения); в GSD-потоке scope —
  фазовый (см. блок GSD ниже).

## Нормы PR

- **SHOULD** держать PR сфокусированным на одной логической единице работы; смешивать в
  одном PR несвязанные изменения (рефакторинг + фича + правка доков) — **WON'T**, потому
  что это раздувает ревью и риск; вместо этого — отдельный PR на каждую логическую единицу.
- **MUST** в описании PR указывать, *что* и *зачем* меняется (мотив, а не только дифф);
  оставлять PR без описания мотивации — **WON'T**; вместо этого — короткое «что/зачем».
- **SHOULD** доводить PR до зелёных проверок (сборка/тесты, см. [build.md](build.md))
  перед запросом ревью.

## Когда коммитить

- **MUST** коммитить логически завершённые атомарные изменения: один коммит = одно
  осмысленное, согласованное изменение, которое не ломает сборку. Сваливать несколько
  несвязанных правок в один «мега-коммит» — **WON'T**, потому что это мешает revert и
  bisect; вместо этого — отдельный коммит на каждое логическое изменение.
- **SHOULD** коммитить часто и небольшими порциями, но каждый коммит **MUST** оставлять
  ветку в согласованном состоянии (без заведомо битой сборки).

## GSD-практики (GSD-тулинг, не общий стандарт)

Этот блок описывает практики GSD-воркфлоу — это **тулинг планирования**, а не общий
git-стандарт проекта. Детали и полный GSD git-workflow — в GSD-доках/командах (`/gsd-*`).
Дублировать полный GSD-workflow здесь — **WON'T**, потому что он живёт в GSD-доках и копия
с ним разойдётся; вместо копии — это краткое упоминание и указатель.

- GSD коммитит планы/состояние в `.planning/` (служебные артефакты процесса, не канон).
- В GSD-коммитах scope — phase-scoped вида `docs(NN):` (где `NN` — номер фазы, напр.
  `docs(02):`); это надстройка над общими Conventional Commits.
- GSD-коммиты несут trailer `Co-Authored-By:` (атрибуция ИИ-агента).
- `.planning/` фильтруется из PR через `gsd-pr-branch` (служебные артефакты не попадают
  в PR в основную ветку).
