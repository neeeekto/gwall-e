# Сборка, запуск, тесты

Реально работающие команды сборки/тестов репозитория — на уровне рецептов, не хрупких
длинных листингов. **Канон по командам — здесь**; раскладка модулей (что в workspace,
что вне) — канон в [structure.md](structure.md) (ссылка, не копия).

**WON'T** документировать команды, которые не запускаются (phantom-команды): база
описывает только реально проверенные рецепты; «как должно бы работать» — **WON'T**.

## Предусловие

- **MUST** иметь Go 1.24.6 и активный `go.work` в корне репозитория. Состав workspace
  перечисляет [structure.md](structure.md) — здесь список не дублируется (**WON'T**,
  чтобы не плодить копии; вместо этого — ссылка на канон).

## Тесты общих пакетов (`pkg`)

**MUST** прогонять тесты общей библиотеки из её модуля:

`cd pkg && go test ./...`

Это рабочий рецепт: в `pkg` есть тесты (`pkg/http`), прогон зелёный.

## Сборка модулей workspace

- **MUST** собирать `audit` из его модуля: `cd services/audit && go build ./...` —
  модуль содержит пакеты (есть `cmd/main.go`), сборка проходит.
- **SHOULD** помнить, что `analytics` — пока модуль-заготовка: в нём ещё нет Go-пакетов,
  поэтому `cd services/analytics && go build ./...` матчит ноль пакетов и печатает
  `matched no packages` — это **не** ошибка. **WON'T** выдавать `analytics` за «собранный
  сервис с кодом»: вместо этого помечать его как заготовку до появления пакетов.

## inventory — WIP, `GOWORK=off`

`inventory` собирается отдельно, **вне** workspace (почему — см.
[structure.md](structure.md), раздел про inventory).

**MUST** запускать команды inventory с `GOWORK=off` из каталога модуля:

`cd services/inventory && GOWORK=off go build ./...`

- **MUST** относиться к этим командам как к **WIP**: `inventory` сейчас **не**
  гарантированно компилируется — рецепт документируется как WIP, **WON'T** выдавать его
  за «проверенно рабочий». Если сборка падает — это ожидаемо для WIP; вместо «починки»
  лесов — следовать правилам границ (`boundaries.md`).

## Фронтенд `web/` (Nx)

Фронтенд — отдельная часть (Nx-workspace, см. [structure.md](structure.md)). Инфра-справка:

- **SHOULD** запускать задачи фронтенда через Nx из каталога `web/`: `npx nx <target>`
  (например `npx nx <target> <project>`).
- **WON'T** фиксировать здесь конкретные непроверенные таргеты как канон: вместо
  жёсткого списка — рецепт-уровень `npx nx`, а список доступных задач смотреть в самом
  Nx-workspace (`web/nx.json` и `project.json` приложений).
