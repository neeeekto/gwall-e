# Authoring-стандарт базы знаний

Этот файл задаёт стандарт того, **как** пишутся все правила в `knowledge/*.md`.
Все доки базы знаний (Phase 2–4) **MUST** следовать ему. Файл сам написан по этому
стандарту и служит его образцом.

Содержимое — на русском (как комментарии в коде); тех-термины и примеры — английские.

## Сила правил: MUST / SHOULD / WON'T

Каждое нормативное правило **MUST** нести ровно один тег силы. Разметка — жирный
префикс в начале правила: `**MUST**`, `**SHOULD**`, `**WON'T**`. Применять единообразно.

- **MUST** — твёрдый инвариант. Нарушать нельзя; нарушение — баг/дефект ревью.
- **SHOULD** — сильная рекомендация. Отклонение допустимо, но **MUST** быть обосновано
  в коде/PR (комментарий или описание).
- **WON'T** — явный запрет: то, чего проект сознательно не делает.

Прозу-хеджирование без тега («prefer», «try», «обычно», «желательно») **WON'T**
использовать в нормативных правилах: вместо неё **MUST** ставить тег. Если у фразы нет
тега — это не правило, а пояснение/контекст, и оно не обязывает.

## Парность «запрет → do»

**MUST**: каждый запрет (`WON'T` / «не делай X») сопровождается предписанной
альтернативой («do»). Формула: не «не делай X», а **«делай Y; X — WON'T, потому что Z»**.
Запрет без альтернативы оставляет агента без выхода и провоцирует случайные «починки».

Примеры формата:

- **MUST** держать факт в одном каноническом доке. Дублировать тот же факт в нескольких
  файлах — **WON'T**, потому что копии расходятся; вместо копии — относительная ссылка
  на канон.
- **SHOULD** держать один топик в одном файле. Складывать несколько несвязанных топиков
  в один мега-файл — **WON'T**, потому что это раздувает контекст-бюджет; вместо этого —
  отдельный файл на топик и ссылка из `README.md`.

## Pointer-over-copy

**SHOULD**: один факт живёт в одном каноническом доке; остальные доки ссылаются на него
относительной markdown-ссылкой, а не копируют текст. Вставлять в доки код, который
протухнет (точные сигнатуры, длинные листинги, хрупкие пути) — **WON'T**; вместо этого
**SHOULD** описывать правило/паттерн на уровне поведения и указывать, где смотреть исходник.

## Размер и дробление

**SHOULD**: один топик = один файл. При превышении ~150–200 строк файл **SHOULD** дробить
на под-топики и связывать ссылками.

Pruning-тест перед добавлением строки: «удаление этой строки приведёт к ошибке агента?»
Если нет — строку **SHOULD** вырезать. Цель — минимальный полезный контекст, а не полнота.

## Никаких phantom-правил

Описывать поведение несуществующих подсистем, фич или файлов — **WON'T**; вместо этого
база документирует только то, что реально есть в репозитории сейчас. Документировать «как
должно быть в будущем» в правилах **WON'T** — для будущего есть `.planning/` (планы) и
раздел «запланировано» в `README.md`. Стабильный ubiquitous-language (`glossary.md`) —
единственное исключение: термины можно фиксировать заранее.

Ссылки **MUST** вести только на реально существующие файлы. Ссылка на ещё не созданный
док — **WON'T**; вместо ссылки — упоминание со статусом «запланировано».

## Статус enforcement

**SHOULD**: где правило механизируемо, помечать его фактическим статусом проверки. Это
**канон легенды** статусов — единственное место, где они определяются; topic-доки
ссылаются на него и **WON'T** переопределять (pointer-over-copy).

Три статуса, точно:

- `hook` — правило проверяется **закоммиченным git-хуком сегодня** (lint / format /
  commit-msg / test через [`lefthook.yml`](../lefthook.yml) + [`.golangci.yml`](../.golangci.yml) /
  commitlint). Доступно локально после bootstrap'а (`make tools` + `npm install` +
  `lefthook install`, см. [build.md](build.md)).
- `convention-only` — правило **review-enforced**: соблюдается ревью, без автоматизации.
- `CI-gated` — **зарезервировано** до появления CI-пайплайна (будущий эпик): тот же
  `.golangci.yml` / `buf` переиспользуются в CI без изменений.

**MUST NOT** помечать правило `CI-gated`, пока в репозитории нет CI-пайплайна
(`.github/workflows`/раннер) — это была бы phantom-claim о несуществующем enforcement.
Вместо `CI-gated` сейчас: **MUST** ставить `hook`, пока правило держит локальный хук, и
`convention-only`, если оно только review-enforced; `CI-gated` — **WON'T** до появления CI.

Уточняющие подпометки у `hook` (depguard): `hook (lint: depguard, biting)` — правило
**кусает сегодня** (ban на импорт снесённого пакета сработает на реинтродукции);
`hook (lint: depguard, dormant)` — правило написано вперёд и **дремлет** (его
path-селектор пока не матчит ни одного Go-файла), активируется по мере появления
кода слоёв.

Статусы **проставлены (Phase 4, ENF-05)**: forward-метки Phase 3 переключены на
фактический механизм, а не ретрофитятся с нуля.
