# gwall-e — L2 Architecture (Platform Vision)

**Статус:** L2-видение (milestone v2.0). Верхнеуровневая карта доменов и направление —
«куда движемся и как». Не контракт реализации: детали каждого домена уточняются, когда
эпик режется в требования/фазы. Дополняем/меняем по ходу.

**Дата:** 2026-06-18
**Core Value:** безопасное и **согласованное** управление парком серверов как услугой.

---

## Что это за платформа

gwall-e управляет парком ~150 000 хостов и VM в дата-центрах. По характеру — **большой
оркестратор над внешними системами**: сами «тяжёлые» операции (профилировка, наливка,
сетевые изменения) выполняют **внешние провайдеры**, gwall-e их дирижирует, храня единый
источник истины и обеспечивая согласованность с владельцами нагрузки.

**Акторы:**
- **Инженеры ДЦ** — физическое обслуживание машин.
- **SRE** — эксплуатация (настройка, обновления), правила автопочинки.
- **Owners** — подразделение/группа, которой **выделены ресурсы** (напр. ML-департамент);
  их нагрузка крутится на хостах; их CMS согласует действия.
- **Админы/разработчики gwall-e** — настройка системы, диагностика.

## Принцип декомпозиции

**Сервис = домен** (DDD bounded context, гексагональная архитектура, БЕЗ CQRS-шины —
канон из v1.0). Каждый крупный домен — отдельный Go-микросервис.

### Кросс-доменный принцип сущностей (инвариант)

> Ключевые сущности (**Project**, **Host**, **VM**, **Owner**) имеют **общую идентичность**
> (один и тот же ID) во многих доменах, но **каждый домен держит свой агрегат** с
> собственными данными и поведением. Для пользователя сущность одна; в доменах ведёт себя
> по-разному.
>
> **Single identity owner:** только **Inventory** создаёт/удаляет идентичность (ID + ЖЦ)
> Project/Host/VM. Остальные домены НИКОГДА не создают новый ID — только локальную проекцию
> по существующему. Никакой «общей таблицы Project» между сервисами — общий ID + контекстные
> локальные модели.

Пример: `Project` — в Inventory это состав хостов/железо/локация и ссылка на owner;
в Network — сетевые политики/IPAM-пул; в Access — owner-роли и права; в Actions — политики
окон/наливок; и т.д.

## Домены

### Бизнес-домены (12)

| # | Домен | Владеет / про что |
|---|-------|-------------------|
| 1 | **Inventory** | Идентичность/ЖЦ Project/Host/VM; железо; локация (ДЦ/модуль/стойка); ссылка `Project → owner`; режим solo-инвентарь ИЛИ sync из внешней инвентори |
| 2 | **Network** | Свитчи, VLAN, IPAM, сетевые шаблоны/конфиги; смена VLAN как действие |
| 3 | **Health / Monitoring** | Runtime: CPU/RAM/логи, health-checks, config-compliance (actual vs target) |
| 4 | **Access** | Вся авторизация: owner-роли (полные права на проект), права/роли, временные гранты (напр. ITDC SSH), IDM-sync, SSH-гранты, права внутри самого gwall-e |
| 5 | **Coordination** ⭐ | approve-before-start с Owner CMS; **CMS-конфиг (URL/auth) + вызов**; локи хостов; глобальные предохранители/лимиты |
| 6 | **Actions** | Единичные операции над хостом (reboot/reimage/profile) — каждая стейт-машина; **каталог наливок** (образы/профили) |
| 7 | **Scenarios** | Кампании плановых массовых работ (окна, drain, shutdown на учения, move owner) — человеко-инициируемые саги |
| 8 | **Remediation** | Авто-починка по правилам SRE (Automation Plot) — реактивный self-healing |
| 9 | **Audit** | Лог всех действий в системе |
| 10 | **Analytics** | Аналитика парка |
| 11 | **Orchestrator** | Кросс-доменные lifecycle-саги (provision сущности через домены; **decommission с вето**) |
| 12 | **Integrations** | Адаптеры/контракты к внешним **провайдерам операций** (profile/reimage/network/reboot). Actions формирует намерение → Integrations исполняет против конкретного провайдера |

### Платформенные сервисы (3)

| Сервис | Про что |
|--------|---------|
| **API Gateway / BFF** | Вход для фронтенда |
| **Search** | Поверх **OpenSearch**, много индексов, consumer-группа на тех же Kafka-событиях → строит поисковые индексы со всех доменов; для людей и машин (read-only query-API) |
| **Notifications** | Уведомления |

### Отложено

- **Host Agent**-кластер: агент на хосте (сбор данных → Health; канал исполнения ← Actions;
  раздача/enforcement SSH-доступа ← Access) + серверная часть (реестр агентов, версии/апдейты,
  каналы связи, allow-list команд). Решение «отдельный домен vs часть Health» — при
  проектировании Health/Access-эпиков.

## Согласованность с Owner (Coordination-контракт)

**Core-value инвариант:** gwall-e **никогда** не выполняет действие без явного approve от
Owner CMS.

```
Намерение (gwall-e)
   → CMS реджектит  ──────────────► отказ
   → CMS принимает и разгружает (async, может длиться ~час, напр. перенос БД)
       → CMS подтверждает готовность окна
           → gwall-e исполняет действие
```

- Процесс **stateful, асинхронный, long-running**.
- Для **массовых работ (Scenarios)** — тот же протокол уведомления + обязательный approve,
  пакетно/по окнам.
- Сверху — **глобальные предохранители/лимиты** gwall-e (могут притормозить даже при approve CMS).
- CMS настраивают **owner'ы проекта** (право даёт Access-роль owner); сам конфиг хранится в
  Coordination; `owner-id` берётся из Inventory-проекции.

## Owner: два слоя

| Понятие | Домен | Смысл / источник |
|---------|-------|-------------------|
| **Owner проекта** | **Inventory** (атрибут `Project.owner`) | Подразделение/группа, которой **выделены ресурсы** (напр. ML-департамент). Приходит из внешней инвентори или задаётся в solo-режиме |
| **Owner-роль** | **Access** | Те, кто обладает **полными правами** на проект: члены owner-группы с определённой ролью в IDM → получают роль `owner` в Access при создании проекта |
| **Временные гранты** | **Access** | Напр. ITDC нужен SSH → выдаются временные точечные права (не owner-роль) |

`OwnershipChanged` (смена владельца проекта, и Scenario «move owner») эмитит **Inventory**.

## Синхронизация доменов (по результатам ресёрча)

**Гибрид с чётким разделением:**

| Что | Механизм |
|-----|----------|
| **Распространение факта об идентичности/ЖЦ** (`ProjectCreated`, `HostRegistered`, `OwnershipChanged`, `HostDecommissioned`) | **Choreography (события)**: Inventory эмитит → домены реактивно строят свой агрегат через ACL |
| **Длинный бизнес-процесс с результатом/компенсацией** (Coordination approve ~1ч, Scenarios, decommission с вето) | **Orchestration-саги / process manager** (отдельный **Orchestrator**-сервис) с persisted state |

**Критическое правило:** факт «Project существует» → событие. Процесс «разгрузить хост по
согласованию» / «снести везде с вето» → сага в Orchestrator. Оркестратор НЕ провижнит
проекции сам — он слушает те же события идентичности.

**Backfill:** **proactive для всех доменов** (каждый материализует проекцию сразу по
событию). ACL-fallback (query в Inventory) держим для гонок порядка. *(Если домен окажется
тяжёлым — точечно переведём на lazy.)*

**Decommission:** гарантированная **saga с вето** — каждый домен может завалидировать
удаление (нельзя удалить Project с хостами → veto), и только при общем «ок» каскадный снос
проекций. Дирижирует Orchestrator.

### Event-backbone: Kafka

```
UoW txn → outbox → relay → Kafka (compacted, partition by entityID) → consumer groups доменов (inbox/dedup)
```

- Outbox+relay (канон v1.0) **не меняется** — Kafka это destination.
- Партиции по `entityID` → порядок в рамках одной сущности.
- Log-compaction по ID → «снапшот идентичности» для онбординга нового домена бесплатно.
- Replay с offset=earliest → backfill нового сервиса.

### Инварианты для записи в архитектуру доменов

1. **Single identity owner** — только Inventory создаёт ID.
2. **Идемпотентность потребителей** — inbox по `eventId`, at-least-once (не exactly-once).
3. **Терпимость к out-of-order** — версия/seq на сущность (last-writer-by-version).
4. **Proactive-by-default**, ACL-fallback на гонки; lazy — исключение для тяжёлых доменов.
5. **ACL на каждом потребителе** — событие → локальный ubiquitous language; осмысленные
   доменные факты (`HostDecommissioned`, не `HostChanged`).
6. **Разделение** «факт идентичности» (event) vs «бизнес-процесс» (saga в Orchestrator).
7. **Replay-safe хендлеры** — backfill не триггерит внешние side-effects.

### Анти-паттерны (избегать)

- Distributed monolith через синхронные команды на провижн проекций.
- Event-carried state «пере/недо» (жирные `EntityUpdated`-дампы либо тощие notification без полей).
- Отсутствие идемпотентности/inbox («полагаться на exactly-once брокера»).
- Скрытые временны́е связи (implicit ordering).
- Choreography для длинного процесса (approve ~1ч цепочкой событий).
- Eager-провижн **пустых** агрегатов туда, где проекция реально не нужна.

## Открытые вопросы (уточняем по ходу)
