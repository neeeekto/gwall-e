Включить разделы:
1. Назначение — этот файл задаёт стандарт авторинга; все доки knowledge/*.md (Phase 2–4) ОБЯЗАНЫ ему следовать.
2. Сила правил — определить три тега и их семантику: MUST (твёрдый инвариант, нарушать нельзя), SHOULD (сильная рекомендация, отклонение требует обоснования), WON'T (явный запрет / чего проект сознательно не делает). Выбрать разметку (рекомендуется жирный префикс `**MUST**` / `**SHOULD**` / `**WON'T**` — это Claude's Discretion из CONTEXT.md; зафиксировать выбор и применять единообразно). Указать: каждое нормативное правило ОБЯЗАНО нести один из тегов; прозу-хеджирование ("prefer", "try", "обычно") без тега — не использовать.
3. Парность запрет→«do» (Pitfall 5) — MUST: каждый запрет сопровождается предписанной альтернативой («do»). Дать формулу: не «не делай X», а «делай Y; X — WON'T, потому что Z». Привести 1–2 коротких примера в этом формате (можно нейтральных/доменно-нейтральных, без описания несуществующих фич — Pitfall 8).
4. Pointer-over-copy — SHOULD: один факт живёт в одном каноническом доке; остальные ссылаются, не дублируют. Не вставлять код, который протухнет (Pitfall 3/6).
5. Размер и дробление — SHOULD: один топик = один файл; дробить файл при превышении ~150–200 строк (Pitfall 2). Pruning-тест: «удаление этой строки приведёт к ошибке агента? нет → вырезать».
6. Никаких phantom-правил — MUST NOT: не описывать поведение несуществующих подсистем/фич; база документирует только то, что реально есть сейчас (Pitfall 8). Стабильный ubiquitous-language (glossary) — исключение.
7. Статус enforcement (задел под Phase 4, ENF-05) — SHOULD: где правило механизируемо, помечать его статусом (CI-gated / hook / convention-only). В Phase 1 это только упоминание стандарта, не сами пометки.

НЕ описывать конкретные доменные правила (язык кода, тесты, архитектуру) — это контент Phase 2–3; здесь только МЕТА-стандарт авторинга. НЕ вставлять fenced-блоки с полным контентом будущих доков. Держать файл лаконичным (целевой объём ~40–90 строк).
